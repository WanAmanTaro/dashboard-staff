INSTITUT AMINUDDIN BAKI (IAB)

====================================================================== 1.
PERANAN DAN OBJEKTIF PEMBANGUNAN
======================================================================

Bertindak sebagai pasukan pembangunan perisian profesional yang terdiri
daripada: - Senior Full-Stack Developer - Solution Architect - Firebase
and Google Cloud Engineer - Google Drive API Integration Specialist -
UI/UX Designer - Database Architect - Cybersecurity Engineer - Quality
Assurance Engineer

Bangunkan sebuah aplikasi web yang lengkap, responsif, selamat dan boleh
digunakan dalam persekitaran sebenar untuk mengurus biodata, maklumat
perkhidmatan, kelayakan akademik, kepakaran, kompetensi, penerbitan,
gambar profil dan sijil semua pegawai di Institut Aminuddin Baki (IAB).

Nama sistem: SISTEM PENGURUSAN MODAL INSAN DAN KEPAKARAN IAB

Tujuan utama: 1. Mengumpulkan semua maklumat pegawai dalam satu
pangkalan data berpusat. 2. Membolehkan setiap pegawai mengemas kini
profil sendiri. 3. Memudahkan Ketua Pusat dan Ketua Jabatan melihat
maklumat pegawai mengikut skop kuasa. 4. Menyediakan direktori kepakaran
untuk mengenal pasti tenaga pakar, fasilitator, penceramah dan
jurulatih. 5. Menjana profil profesional pegawai secara automatik dalam
PDF. 6. Menganalisis kapasiti, taburan dan jurang kepakaran organisasi.
7. Menyimpan gambar asal dan semua dokumen sijil dalam satu akaun Google
Drive pemilik storan yang ditetapkan. 8. Menyokong perancangan
pembangunan kapasiti dan keputusan pengurusan berasaskan data.

PENTING: Jangan hasilkan mockup statik semata-mata. Bangunkan aplikasi
sebenar dengan fungsi yang disambungkan kepada authentication, database
dan Google Drive apabila konfigurasi luaran disediakan. Jangan mendakwa
integrasi telah berjaya jika belum diuji dengan akaun dan projek
sebenar.

2. KEPUTUSAN DAN KONFIGURASI PROJEK
======================================================================

Gunakan konfigurasi berikut:

-   Frontend: React + TypeScript.
-   UI: Tailwind CSS atau komponen UI moden yang stabil.
-   Authentication: Firebase Authentication.
-   Kaedah login: Google Sign-In DAN Email/Password.
-   Database: Firebase Firestore.
-   File storage: Google Drive API.
-   Backend: Firebase Cloud Functions atau Google Cloud Run.
-   Backend authentication: Firebase Admin SDK.
-   Chart: Recharts atau library visualisasi setara.
-   PDF generation: library PDF yang sesuai dan stabil.
-   Excel export: library yang sesuai dan stabil.
-   Hosting: Firebase Hosting atau platform deployment yang serasi.

Google Drive: - Gunakan satu akaun Google individu yang ditetapkan
sebagai PEMILIK STORAN SISTEM. - Akaun ini bukan akaun Google setiap
pegawai. - Semua gambar asal, gambar paparan, sijil dan PDF yang dijana
disimpan dalam Drive pemilik storan. - Pegawai memuat naik fail melalui
aplikasi; backend menyimpan fail menggunakan OAuth pemilik storan. -
Jangan minta setiap pegawai menyambungkan Drive peribadi
masing-masing. - Sediakan pelan kesinambungan, pemulihan akaun dan
pemindahan pemilikan storan kepada organisasi. - Aktifkan MFA pada akaun
pemilik storan. - Jangan jadikan dokumen awam.

PENTING TENTANG DUA JENIS OAUTH: Firebase Google Sign-In digunakan untuk
mengesahkan identiti pegawai. Google Drive OAuth digunakan secara
berasingan untuk memberikan backend kebenaran mengurus fail dalam Drive
pemilik storan. Jangan campurkan kedua-dua aliran pengesahan ini.

4. ROLE-BASED ACCESS CONTROL (RBAC)
======================================================================

Tetapkan lima tahap pengguna:

L1 — Ketua Pusat L2 — Ketua Jabatan L3 — Pensyarah L4 — Bukan Pensyarah
(Pegawai) L5 — Bukan Pensyarah (Bukan Pegawai)

Admin ialah peranan pentadbiran berasingan daripada lima tahap tersebut.

Hak akses:

KETUA PUSAT (L1) - Melihat semua profil pegawai dalam pusat. - Melihat
Dashboard Pusat. - Melihat Dashboard Jabatan. - Melihat Direktori
Kepakaran keseluruhan. - Melihat Analisis Kapasiti Kepakaran. - Tidak
boleh mengubah profil individu secara senyap. - Sebarang pembetulan
pentadbiran mesti direkodkan dalam audit log.

KETUA JABATAN (L2) - Melihat profil pegawai jabatan sendiri. - Melihat
Dashboard Jabatan sendiri. - Melihat kepakaran jabatan sendiri. -
Mengakses laporan jabatan. - Tidak boleh mengubah profil individu tanpa
proses dan kebenaran yang ditetapkan.

PENSYARAH (L3) - Melihat dan mengemas kini profil sendiri. - Memuat naik
gambar dan sijil sendiri. - Melihat direktori atau maklumat lain yang
dibenarkan.

BUKAN PENSYARAH (PEGAWAI) (L4) - Melihat dan mengemas kini profil
sendiri. - Memuat naik gambar dan dokumen sendiri. - Akses kepada
maklumat lain mengikut kebenaran.

BUKAN PENSYARAH (BUKAN PEGAWAI) (L5) - Melihat dan mengemas kini profil
sendiri mengikut kebenaran. - Akses terhad kepada modul organisasi.

ADMIN - Mengurus pengguna, role, pusat, jabatan, konfigurasi, kategori,
storan dan sistem. - Admin tidak boleh memberikan role Admin kepada
dirinya sendiri melalui frontend. - Perubahan role mesti disahkan di
backend dan direkodkan dalam audit log.

Gunakan RBAC di backend dan Firestore Security Rules. Jangan hanya
menyembunyikan menu atau butang di frontend. Setiap endpoint mesti
menyemak Firebase ID Token, status akaun, role, skop pusat/jabatan dan
pemilikan rekod.

7. GOOGLE DRIVE — PEMILIK STORAN
======================================================================

Gunakan satu akaun Google individu yang ditetapkan sebagai pemilik
storan aplikasi.

Struktur folder:

IAB_HUMAN_CAPITAL_SYSTEM/ 01_PROFILE_PHOTOS/ 02_ACADEMIC_CERTIFICATES/
03_PROFESSIONAL_CERTIFICATES/ 04_COMPETENCY_CERTIFICATES/
05_TRAINING_CERTIFICATES/ 06_PUBLICATIONS/ 07_GENERATED_PROFILES/

Gunakan Staff ID unik sebagai folder atau pengenal folder pegawai.
Jangan gunakan nombor kad pengenalan sebagai nama folder.

Google Drive OAuth: - Gunakan OAuth 2.0 Authorization Code Flow. -
Gunakan offline access untuk backend apabila diperlukan. - Gunakan
least-privilege scope, bermula dengan drive.file jika memenuhi keperluan
sebenar. - Nilai scope dan keperluan folder perlu diuji. Jangan menaik
taraf scope tanpa justifikasi. - Simpan refresh token secara encrypted
di backend atau Google Secret Manager. - Jangan dedahkan client secret,
access token atau refresh token dalam frontend. - Sediakan reconnect
apabila kebenaran dibatalkan. - Sediakan status sambungan dan ujian
sambungan. - Sediakan pemulihan apabila token tamat atau ditarik balik.

PENTING: Jika aplikasi perlu mengurus folder sedia ada atau fail yang
tidak dicipta oleh aplikasi, sahkan terlebih dahulu sama ada drive.file
mencukupi. Pilih scope paling minimum yang benar-benar menyokong reka
bentuk tersebut.

Gunakan resumable upload bagi fail besar atau sambungan tidak stabil.

Pastikan operasi upload dan simpan metadata mempunyai pengendalian
kegagalan. Jika fail berjaya dimuat naik tetapi Firestore gagal
menyimpan metadata, rekodkan keadaan tersebut dan sediakan proses
reconciliation atau cleanup supaya tidak berlaku fail yatim.

Jangan mendakwa upload berjaya sebelum Google Drive mengesahkan
penciptaan fail dan metadata Firestore berjaya disimpan.

19. KRITERIA PENERIMAAN SISTEM
======================================================================

Sistem hanya dianggap bersedia untuk UAT apabila:

A. AUTHENTICATION - Google Sign-In berfungsi. - Email/Password
berfungsi. - Account linking diuji. - Akaun tidak diluluskan tidak boleh
mengakses data.

B. PROFILE - Pengguna boleh mengemas kini profil sendiri. - Pengguna
tidak boleh mengubah profil orang lain. - Data kekal selepas logout dan
login semula.

C. PHOTO - Gambar asal disimpan dalam Google Drive. - Gambar paparan
disimpan berasingan. - Crop dan positioning berfungsi. - Gambar asal
tidak berubah.

D. CERTIFICATE - Sijil sebenar berjaya disimpan dalam Drive. - Nama
sijil dipaparkan. - Pautan hanya boleh digunakan oleh pengguna yang
dibenarkan. - Fail tidak didedahkan secara public.

E. DASHBOARD - Statistik berasal daripada Firestore. - Filter
berfungsi. - Nilai kosong tidak dianggap sebagai sifar. - Skop data
mengikut role.

F. STRATEGIC MODULES - Direktori kepakaran boleh mencari data sebenar. -
PDF dijana berdasarkan profil sebenar. - Analisis kapasiti menggunakan
kaedah pengiraan yang jelas.

G. SECURITY - Backend mengesahkan Firebase ID Token. - RBAC diuji. -
Security Rules diuji. - Audit log merekodkan aktiviti sensitif. - Secret
tidak terdedah dalam frontend.

H. DEPLOYMENT - Aplikasi boleh diakses melalui URL deployment. - Backend
aktif. - Environment variables dan secrets dikonfigurasikan. - Backup
dan recovery didokumenkan.
